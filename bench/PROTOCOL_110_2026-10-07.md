# 1.10.0 benchmark protocol (aarch64 Debian, 2026-10-07)

Written BEFORE the run, so the method cannot be fitted to the results.

## Questions this must answer

1. Does the shared doclen copy remove the rare-term throughput drop-off (I6)? -- A/B,
   same binary, `pg_fts.shared_doclen` on vs off, same host, alternating.
2. Does it cost anything single-client? -- latency bands, on vs off.
3. Where does pg_fts 1.10.0 stand against the other PostgreSQL BM25 extensions **as
   they ship today**, on aarch64? -- one host per engine, same corpus and queries.

## Rig

- EC2 **r7gd.4xlarge**: AWS Graviton3 (Neoverse-V1), 16 vCPU, 128 GiB, 1x 950 GB local
  NVMe (instance store), us-east-2. One instance per engine; no engine shares a host.
- Debian 13 (trixie) arm64 official AMI, kernel as shipped. No tuning beyond: data
  directory on XFS on the local NVMe; CPU frequency governor untouched (Graviton has no
  frequency scaling exposed).
- PostgreSQL **17.10** from source, `-O2 -g -fno-omit-frame-pointer`, identical on every
  host. `shared_buffers=32GB`, `work_mem=256MB`, `maintenance_work_mem=8GB`, `jit=off`,
  `autovacuum=off` during measurement, `max_connections=200`.
- Engines (latest release on 2026-10-07):
  - pg_fts **1.10.0** (this release), built from the release tree.
  - pg_textsearch **v1.5.1** (Timescale), built from its tag.
  - pg_search **v0.26.0** (ParadeDB), the official `trixie_arm64` .deb for PG17 --
    a source build of a Rust/pgrx extension would test our toolchain, not theirs.
  - VectorChord-bm25 **0.3.0**, the official arm64 .deb for PG17.
  Each engine's build/version is recorded in its run log (git describe / dpkg -s).

## Corpus

English Wikipedia (`wikimedia/wikipedia`, config `20231101.en`), first **2,188,038**
articles in file order, one row per article, `content = title || ' ' || body`. md5 of the
TSV checked on every host. Each engine indexes `content` with English stemming (or its
closest equivalent; differences in tokenization are reported, not hidden: each engine's
match count for the three probe terms is shown next to a regex ground truth).

## Timing

- Latency: 8 executions per query inside ONE `psql` session with `\timing`, median of
  the last 5 (the first 3 absorb plan caching and buffer warm-up); 3 independent sessions
  ("passes") per band; the table shows the median of the 3 pass-medians and the pass
  spread. Cache state: index and heap prewarmed (`pg_prewarm`), warm runs only -- the
  question is CPU efficiency of the index, not disk.
- Throughput: `pgbench -n -f <one query> -c C -j min(C,8) -T 30`, C in {16, 32, 64},
  2 passes, after a 10 s warm-up at C=8. 16 vCPU, so 32 and 64 are 2x/4x oversubscribed
  on purpose: that is the regime where I6 appeared.
- No `/usr/bin/time` around psql; no single-run numbers.

## Correctness gate (before any timing is believed)

- Every band returns k rows (or the full match set) on every engine.
- pg_fts: shared on vs off return identical ids and distances (ranked bands) -- the A/B
  measures speed of the same answer.
- Match counts vs regex ground truth for the probe terms, per engine.

## What is NOT claimed

- Nothing about write throughput, build time beyond the one measured build, or
  multi-node setups.
- No comparison with numbers from other hardware, other days, or vendor material.
