# Approach A results (aarch64 Debian, 2026-10-07/08)

Protocol: `bench/PROTOCOL_A_2026-10-07.md`, written before the run (the 1.10.0 protocol plus
an on-host pg_fts A/B, an expression-index build, four extra bands and a cold band).
Raw data: `bench/data_A_2026-10-07/run/`. pg_fts branch `approach-a` at **39b6a42** (binary
md5 `4486203a`), released as **1.11.0** (an earlier version of this line said the release
differed only in a comment and a GUC description string; it adds, after that commit, the
VACUUM pending-delete fix and the four concurrency fixes (CHANGELOG 1.11.0), which change
the write, flush, free and truncate paths and not the query traversals. Timings were not re-
run on the release binary (unmeasured); on a 600k-row index built locally, 39b6a42 and the
release give identical sizes after build, VACUUM and merge, and identical counts and top-20
on five bands, `data_A_2026-10-07/release/size_results_39b6a42_vs_release.txt`), against the
**1.10.0** release built from its PGXN zip (`80c9ffdc`), on the same host and the same index
files.

EC2 r7gd.4xlarge (Graviton3 Neoverse-V1, 16 vCPU, 128 GiB, local NVMe), Debian 13 arm64,
PostgreSQL 17.10 from source, settings as 1.10.0.  Corpus: 2,188,038 Wikipedia articles,
md5 `f5939e85...` verified on every host.  One host per engine.

## Correctness gate (before any timing)

- pg_fts: both arms return the same ids and the index's own scores (within 1e-9) on 11 of
  12 bands and the count (`gate_*`).  The 12th, `film | music | album | band` (4 terms, the
  MaxScore path), differs: **1.10.0 returns a wrong top-10** (none of the true top-10;
  CHANGELOG 1.11.0, "Fixed").  The approach-a arm matches an exhaustive reference
  computed from the stored documents with the index's statistics and length quantization
  (`or4_oracle.txt`: 3 cases, 0 differ).  1.10.0 is not timed on that band.
- Every band returns k rows on every engine that can express it.
- Match counts vs regex ground truth: unchanged from 1.10.0 (pg_fts and pg_textsearch
  10,875 / 24,097 / 734,896 against regex 10,898 / 24,148 / 733,960; pg_search 10,898 /
  24,152 / 735,955).

pg_textsearch's boolean and phrase forms (`content @@ to_tsquery(...)` with a BM25 ORDER BY)
are evaluated by a sequential scan; each execution hits the 300 s statement timeout, as in
1.10.0, so the two added AND/phrase bands were stopped after one timed-out pass ("not run").
Its OR-of-terms ranked form (`to_bm25query('film music album band')`) is a normal index scan
and is shown.  Phrase bands use pg_fts's `positions = on` index; all other pg_fts bands
use the default index.

Against itself, approach-a is faster than 1.10.0 on every band: 1.4-1.9x for rare, mid, OR
and the small AND; 3.2x for `world & war` and the `"world war"` phrase; 6.7-10.5x for
common top-k, `united & states` and the `"united states"` phrase.  The pass spreads of the
two arms never overlap.  Against the field, approach-a has the lowest latency on 9 of 12
bands; pg_search is lower on `world & war` (5.73 vs 5.98) and on the 4-term OR (13.92 vs
13.99, inside the spreads).

Build times were measured with the first approach-a binary of this run (`c9c4079c`, tree
b78ccaa); the two later commits (39b6a42 is the final one) change only read-path prefetch,
not the build or merge code.  The expression-index row is the fair comparison: every other engine analyses text inside
its build.  1.10.0's published "298 s build" did not include the 995 s column fill, and a
fresh 1.10.0 index was 2.4x its packed size until a manual `fts_vacuum`.  pg_search still
builds 3.6x faster.  On the development host, a stored-column build (105 s) spent 42.2 s
in the single-backend collapse merge and 23.7 s in the single-backend pack that replaces
`fts_vacuum` (DEBUG1 timings, `data_A_2026-10-07/a3_merge_notes.txt`); the rest is the
parallel heap scan.  The expression-index build also analyses the text inside that scan.

## What this does not show

- The on-disk format is unchanged (the tighter
  block bounds use an existing header field; old segments keep the old bounds until a
  merge rewrites them, and are read correctly either way).
- The 1.10.0 published numbers stand for the 1.10.0 release.  Re-measured here: rare k10
  1.07 ms (published 1.16), common k10 8.48 (8.50), settled rare c16 17,496 tps (17,051).
  Phrase is the exception: 24.95 ms here against the published 36.85.  The published figure
  is on a positions index built (and `fts_vacuum`ed) by 1.10.0; here both arms read the
  positions index approach-a built, whose block headers carry the tighter A1 bound in a
  field 1.10.0 also reads, so the 1.10.0 arm's WAND skips more.  That reading is unmeasured:
  1.10.0 was not timed on its own positions index in this run.  The 1.10.0 column is
  therefore "1.10.0 code on an approach-a index", which flatters 1.10.0, not approach-a.
- During this run, three intermediate approach-a binaries were measured and rejected; their
  data are kept (`fts/pre_final_a1`, `fts/pre_final_a3`).  The first sent per-page
  `posix_fadvise` along contiguous chains, which defeated kernel read-ahead and made cold
  common-term queries slower than 1.10.0.  The next read the relation size per chain page,
  costing 9% of `count(*)` throughput.  The tables above are the final binary only.
