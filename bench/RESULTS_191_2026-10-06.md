# pg_fts 1.9.1 vs pg_textsearch 1.4.0 (2026-10-06)

The release benchmark for 1.9.1. Same rig and protocol as `RESULTS_190_2026-10-01.md`:
EC2 r6id.4xlarge, Debian 13.7, PostgreSQL 17.10 from source, 2,188,038 Wikipedia rows
(md5-identical TSV on every host), one engine per host, 8 runs per query in one session,
median of the last 5, 3 independent passes; concurrency 16/32/64 clients x 30 s x 2
passes. pg_textsearch v1.4.0 was re-run the same day on its own host as the control.

Data: `data_191_2026-10-06/` (`lat_fts`, `lat_pgts`, `conc_fts`, `conc_pgts`,
`layout_ab`, `final_*.txt`).

## Correctness

- Counts identical to pg_textsearch and to regex ground truth (10,875 / 24,097 / 734,896;
  regex 10,898 / 24,148 / 733,960 -- regex also matches non-word-boundary forms the
  analyzer splits differently).
- Phrase: `fts_count` of `"united states"` = 361,465 (regex 362,305).
- Lazy phrase gate == collect path (`pg_fts.lazy_phrase = off`), ids and distances, for
  7 phrases (2-, 3- and 5-term, NEAR, a no-match phrase) x k in {1, 10, 100, 1000}:
  28/28 on the final 1.9.1 tree (`phrase_gate_corpus.txt`, script
  `phr_gate_corpus.sh`); every k returns rows wherever the phrase occurs.
- In-place upgrade from the released 1.9.0 zip (index with tombstones, no REINDEX): count
  == seqscan and top-20 == heap `fts_bm25` reference for 4 queries at each of three steps
  -- 1.9.1 binary on 1.9.0 SQL, after `ALTER EXTENSION ... UPDATE`, and after writes,
  merge and vacuum on 1.9.1 (12/12; `upgrade_qual_190_to_191.txt`, built from the
  released 1.9.0 and 1.9.1 zips).
- `phrase_gate` regression test, with planted mutants: dropping the adjacency check fails
  17 cases, a fixed step distance fails 1, dropping the per-posting delta reset fails 37.

### A code-layout regression found and removed before release

The first 1.9.1 build was ~5% slower on single-term common queries (7.5-7.9 vs
7.1-7.2 ms) although the dense-scoring loop those queries run was untouched. Bisection on
one host (`layout_ab/`):

- sparsemap 5.8.1 alone: same as 1.9.0 (7.09-7.19 ms);
- reverting the gate short-circuit, or making the new phrase functions noinline: no change;
- the dense loop's own machine code moved inside its caller; its instructions differed only
  in register allocation and placement.

Making `fts_search_dense1` `pg_noinline` restored it. 5 alternating server starts on
each of two hosts:

| host | 1.9.0 | 1.9.1 first build | 1.9.1 + noinline |
|---|---|---|---|
| dev | 7.10-7.22 | 7.54-7.94 | 7.00-7.03 (3 starts), 7.60 / 7.85 (2) |
| conc | 7.06-7.25 | 7.53-7.77 | 7.01-7.10 (5 starts) |

The final binary then measured 7.06-7.15 and 6.99-7.02 ms on two more hosts. It is a
layout effect, not an algorithmic one, and the code says so at the function.

latency is equal or better: different hosts, not re-measured on one host, recorded as
unexplained.

## Rare-term throughput vs client count (ROADMAP I6)

Diagnosed, not fixed; see `PLAN_I6_SHARED_DOCLEN_2026-10-06.md` and
`data_i6_2026-10-06/`. All of the extra per-transaction cost at 64 clients is in
`bm25_doclen_cursor_lookup`. Each backend holds a private ~4.8 MB copy of the document
length array, and 64 copies do not fit in L3. A diagnostic build with one shared copy was
flat at 12.3k / 12.5k / 12.6k tps.
