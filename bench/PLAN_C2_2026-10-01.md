# C2: exhaustive dense scoring for high-df single-term ranked top-k (2026-10-01)

Plan for the last losses vs pg_textsearch 1.4.0 after A + C1 (`RESULTS_AC_PGTS_2026-10-01.md`):
common k100 (14.67 vs 13.87 ms), common-term throughput (562 vs 650 tps).

## What the profile says (efca0cf, `year` k10, Debian 13 dev host, perf srcline)

67% `bm25_topk_candidates_range` + 14% `wand_load_block` + 9% doclen lookup. By line,
the biggest single items are the pivot loop and the block-max bound check
(pg_fts_am_scan.c:3640-3662) and the `wand_contrib_cur` call (:3718-3720), each run once
per posting. `NOTE_WAND_PRUNING_2026-09-04.md` measured that on this corpus BMW skips ~9%
of `year`'s blocks. So for a common term the WAND machinery is pure overhead: per posting it
sorts cursors, accumulates `max_contrib`, computes a block-max bound and compares it, and
only THEN scores. A term this common gets almost no benefit from pruning.

## The change (no on-disk format change)

For a query that is a **single plain term** (no operators, no prefix/fuzzy/regex/weight),
in **one segment**, whose df is above a threshold, skip WAND. Instead:

1. decode each 128-posting block's docids + tf columns in one `bm25_for_unpack` pass each
   (the existing decoder), not per posting via `bm25_for_get`;
2. score every posting with a **precomputed 256-entry length-norm table** indexed by the
   quantized doclen byte (C1's slot array gives the byte directly), so per posting it is
   two array reads, one multiply-add and one divide;
3. keep a top-k min-heap with the same (score, TID) eviction order as WAND
   (`scored_worse`), so results are identical, ties included.

Exactness: this scores EVERY posting and keeps the true top-k under the same total order
WAND uses. It is the reference algorithm WAND approximates, so it cannot miss a document.
The rule-2 check is that it returns byte-identical results to the WAND path on every
(query, k) tested.

Why not the "dense bitmap containers" in the dream's C: that needs a format change
(dual-read + in-place upgrade). The measured bottleneck is per-posting control overhead,
not posting decode or I/O, so a scalar exhaustive loop over the existing format attacks it
directly. Containers stay the upgrade path if this does not close the gap.

## Gate

- Threshold `df >= 32768` (about 256 blocks), and only when WAND is unlikely to prune.
  Exposed as GUC `pg_fts.dense_score_min_df` (0 disables) so it can be A/B'd and tuned.
- Falls back to WAND for: multiple segments (to keep this first version simple), tombstones
  (would need the per-segment skip; tombstoned docs are skipped exactly as WAND does --
  include it, it is cheap), a docid range (parallel worker slice), v3 inline-doclen
  segments.

## Measurement plan

1. A/B on the dev host: `efca0cf`+gallop vs C2, 5x alternated, all 9 bands; identical
   results on all 14 top-k lists plus a dedicated exact-k sweep across df.
2. A df sweep (terms from 10k to 735k) to place the threshold where dense beats WAND.
3. Head-to-head re-run vs pg_textsearch on fresh hosts.
