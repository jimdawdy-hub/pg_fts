# pg_fts 1.10.0 release benchmark: aarch64, four PostgreSQL BM25 engines (2026-10-07)

Protocol fixed before the run: `PROTOCOL_110_2026-10-07.md`. Raw data, scripts and every
engine's setup log: `data_110_2026-10-07/`. Nothing here is estimated, extrapolated, or
taken from another machine or a vendor.

## Setup

| | |
|---|---|
| Hardware | AWS EC2 **r7gd.4xlarge**: Graviton3 (Neoverse-V1), 16 vCPU, 128 GiB RAM, 32 MB L3, local NVMe instance store |
| Isolation | **one instance per engine**, same instance type, same AZ family, launched the same day; nothing else running |
| OS | Debian 13.7 (trixie) arm64, official AMI, no kernel tuning; data on XFS on the instance-store NVMe |
| PostgreSQL | **17.10 built from source** on every host, identical flags (`-O2 -g -fno-omit-frame-pointer`) |
| Server config (all engines) | `shared_buffers=32GB`, `work_mem=256MB`, `maintenance_work_mem=8GB`, `jit=off`, `autovacuum=off`, `max_connections=200`, parallel workers 16 |
| Corpus | English Wikipedia, `wikimedia/wikipedia` `20231101.en`, first 2,188,038 articles, `content = title + ' ' + body`; TSV md5 `f5939e85...` identical on every host |

| Engine | Version | Install | Index definition |
|---|---|---|---|
| **pg_fts** | **1.10.0** (this release) | source, release tree | `USING fts (to_ftsdoc('english', content))` (stored `ftsdoc` column), then `fts_vacuum` |
| pg_textsearch | **1.5.1** (Timescale; commit `fa142d04`) | source, tag `v1.5.1` | `USING bm25(content) WITH (text_config='english')` |
| pg_search | **0.26.0** (ParadeDB) | official `trixie_arm64` .deb (+ pgvector 0.8.7, a hard dependency, from source) | `USING paradedb (id, (content::pdb.simple('stemmer=english'))) WITH (key_field='id')` |
| VectorChord-bm25 | **0.3.0** (+ pg_tokenizer 0.1.1) | official arm64 .debs | pg_tokenizer's documented English analyzer (Unicode segmentation, lowercase, NFKD, NLTK stopwords, Porter2 stemmer) + custom model trained on this corpus; `USING bm25 (emb bm25_ops)` |

Each engine used its documented query form: pg_fts `@@@` + `ORDER BY d <=> q`;
pg_textsearch `ORDER BY content <@> to_bm25query(...)` (boolean bands: its documented
`@@ to_tsquery` filter + that ranking); pg_search `|||` / `&&&` / `###` + `ORDER BY
pdb.score(id) DESC`; VectorChord `ORDER BY emb <&> to_bm25query(...)`.

**Timing.** Latency: 8 executions per query in one `psql` session with `\timing`, median of
the last 5; 3 independent sessions per band; reported as the median of the 3 session
medians, with the largest session-to-session spread. Warm cache (table and index
`pg_prewarm`ed): this measures index CPU efficiency, not disk. Throughput: `pgbench -n -f
<query> -T 30`, 16/32/64 clients (`-j` = min(clients, 8)), 2 passes after a 10 s warm-up;
every host was checkpointed and idle for 60 s first, and runs were repeated once to check
stability (both runs in the data directory; the table uses the settled run).

**Correctness checks.** Every band returned k rows on every engine (or timed out, marked).
Match counts against a regex over the raw text:

| term | regex | pg_fts | pg_textsearch | pg_search | VectorChord |
|---|---|---|---|---|---|
| slovakia | 10,898 | 10,875 | 10,875 | 10,898 | n/a (no count) |
| hungary | 24,148 | 24,097 | 24,097 | 24,152 | n/a |
| year (stemmed: year/years) | 733,960 | 734,896 | 734,896 | 735,955 | n/a |

pg_fts and pg_textsearch both use PostgreSQL's `english` configuration, so they agree
exactly; pg_search uses Tantivy's tokenizer + Snowball stemmer; the small differences are
tokenization, not missed documents. Top-10 overlap between engines is 6-10 of 10 per term
(`*/top10.txt`): different stemmers and BM25 length normalization rank near-ties
differently.

## What the numbers say

- **pg_fts leads** the rare/mid-term ranked bands under load (1.2-1.7x pg_textsearch,
  2.6-3.2x pg_search), every boolean band, and exact counts (47x pg_search single-client,
  25-88x under load). It has the smallest index (25% smaller than pg_textsearch, 58%
  smaller than pg_search).
- **pg_search leads** common-term ranking (3.5x pg_fts single-client at k=10, 2.5-3.0x
  under load) and phrase (3.3x). Both are where Tantivy's block-max skipping and
  positional index pay off; they are the honest gaps.
- **pg_textsearch** is the fastest single-client rare term (1.00 vs 1.16 ms) and loses
  throughput as clients increase (14.1k -> 12.4k), where pg_fts no longer does.
  Its boolean and phrase forms are filters evaluated by a sequential scan of the table
  (its README: "not yet optimized as a single index scan"); on 2.19M rows each query
  exceeded the 300 s cap. They are reported as timeouts, not omitted.
- **VectorChord-bm25** is reported as measured, with a caveat: its index came out at 41 GB
  for a 2.7 GB `bm25vector` column, and queries read ~42k buffers each. That is not
  consistent with its own published performance, so this setup (a corpus-trained custom
  vocabulary of 5.1M tokens, which is what pg_tokenizer's documented English recipe
  produces on Wikipedia) is likely a poor fit for it rather than representative. A
  pretrained vocabulary (e.g. `bert`) would change both its size and its ranking
  behaviour; that was not measured.

## The I6 fix, isolated (same host, same binary, `pg_fts.shared_doclen` on vs off)

`data_110_2026-10-07/i6_ab/`. Restart between arms; 2 alternating passes; correctness first:
21/21 ranked (query, k) cases identical between shared, per-backend and cursor paths.

| query | clients | shared (1.10.0 default) | per-backend copies (1.9 behaviour) | ratio |
|---|---|---|---|---|
| rare top-10 | 16 / 32 / 64 | 16,958 / 16,738 / 16,654 | 17,034 / 14,875 / 13,283 | 1.00 / 1.13 / 1.25 |
| mid top-10 | 16 / 32 / 64 | 17,250 / 17,294 / 17,246 | 13,762 / 14,271 / 14,130 | 1.25 / 1.21 / 1.22 |
| common top-10 | 16 / 32 / 64 | 1,904 / 1,882 / 1,873 | 1,846 / 1,854 / 1,844 | 1.03 / 1.01 / 1.02 |

A per-transaction CPU profile at 64 clients (`perf_c64_*.txt`) shows the whole difference
in one function: `bm25_doclen_cursor_lookup` costs 21.2 units per transaction with private
copies and 6.9 with the shared copy, every other symbol within 0.5 units. Rare-term
throughput is now flat from 16 to 64 clients. Mid-term gained even at 16 clients: its
private-copy working set exceeds L3 (32 MB on Graviton3) at fewer backends than the
rare term's does.

## Release qualification (same tree as measured)

- aarch64 (`gate_aarch64.txt`): fuzz ALL CLEAN; regression 10/10 + isolation 2/2; all 11
  TAP files (127 tests: crash recovery, replication, corruption, encodings, concurrency,
  segment cap, vacuum, doclen sidecar, delete-heavy vacuum, shared doclen); coverage line
  91.7%, function 97.5%, branch 73.1% (gate 73%).
- x86-64 (nix): installcheck and TAP on PostgreSQL 17 and 18.
- In-place upgrade from the released 1.9.1 zip, index with tombstones, no REINDEX:
  count == seqscan and top-20 == heap `fts_bm25` for 4 queries at each of three steps
  (1.10.0 binary on 1.9.1 SQL; after `ALTER EXTENSION`; after writes, merge, vacuum):
  12/12 (`upgrade_qual_191_to_110.txt`).
- Failure modes of the shared copy, on the 2.19M index (`i6_ab/*_probe*.sh`): a query
  cancelled while building it (7 cancel points) leaves no stranded slot and the next
  query publishes normally; with `/dev/shm` filled to 64 KB free, ranked queries answer
  correctly from a private copy and the shared copy appears once space is freed; with a
  cursor holding a merged-away segment's copy, 6 newly flushed segments all started on
  fresh blocks (the page recycle gate), so a stale copy is never matched.
