# pg_fts 1.9.0 vs pg_textsearch 1.4.0 (2026-10-01)

The release benchmark for 1.9.0. Same rig and protocol as `RESULTS_AC_PGTS_2026-10-01.md`
(EC2 r6id.4xlarge, Debian 13.7, PostgreSQL 17.10 from source, 2,188,038 Wikipedia rows,
md5-identical TSV on every host, 8 runs / median of last 5 x 3 passes, concurrency 16/32/64
clients x 30 s x 2 passes). pg_textsearch v1.4.0 numbers are from the same day's Debian
run (`data_h2h_2026-10-01/lat_pgts`, `conc_pgts`); it did not change.

pg_fts arm: `5f6ef76` = the 1.9.0 C code (the release commit only adds the version bump,
SQL upgrade script and docs). Data: `data_h2h_2026-10-01/rerun2_lat_fts`,
`rerun2_conc_fts`. An earlier concurrency host for this arm was torn down before it
finished (`rerun2_conc_fts_PARTIAL_torn_down_early/`, kept for the record); the full run
is a separate host.

## Correctness

- Counts identical to pg_textsearch and to regex ground truth (10,875 / 24,097 / 734,896).
- `parity_check.sh` 10/10 on the latency host.
- On the dev host, same build: dense scoring == WAND on 64/64 (term, k) lists over 16
  terms with df 157k-1.17M and k up to 1000; exact top-k on 28/28 OR (query, k) pairs.
- In-place upgrade from a released 1.8.6 index with tombstones: counts == seqscan and
  top-20 scores == heap `fts_bm25` before and after `ALTER EXTENSION`, and after writes
  (`pgfts_upgrade_qual.sh`).

## Where it still loses, and what is known

- **Phrase, 3.2x.** pg_fts materializes all 361k phrase matches before ranking;
  pg_textsearch ranks the terms and rechecks the phrase on candidates. ROADMAP I5.
- **Rare-term tps falls 16 -> 64 clients (12.4k -> 8.6k).** It stays ahead of
  pg_textsearch, which is flat. Measured on the dev host:
  - not lock waits;
  - not the one-time 28 ms per-backend slot build (unchanged at T=60);
  - not CPU pinning (the same fall with 8 and with 16 CPUs);
  - it follows the number of concurrent BACKENDS at fixed work (16 / 32 / 64 backends:
    12.4k / 10.5k / 8.4k queries/s);
  - `bm25_doclen_cursor_lookup`'s CPU share rises 17% -> 46% from 16 to 64 backends.

  The leading hypothesis -- each backend's own 4.8 MB length array competing for the
  54 MB L3 -- is unconfirmed (no hardware counters on this instance type). ROADMAP I6.
